Token Rescoping (Downscoping) — RFC 8693 Token Exchange

Exchange a powerful token for a narrower one — the roles scope is intentionally omitted so the new token carries no realm_access.roles claim. This enforces least-privilege when delegating access to a sub-component that should not inherit admin rights.

{# ── LEFT — How it works + exchange result ────────────────────────────────── #}
How Token Rescoping Works
  1. A service holds a token with full scopes (including roles).
  2. It wants to call a sub-component that should not have admin rights.
  3. It calls the token endpoint with grant_type=token-exchange, passing its own token as subject_token but requesting only scope=openid email profile — no roles.
  4. Keycloak issues a new, narrower token:
    • No realm_access.roles claim
    • Same sub and azp as the original
  5. The sub-component receives a token that cannot escalate privileges.
POST /realms/demo/protocol/openid-connect/token
grant_type = urn:ietf:params:oauth:grant-type:token-exchange
client_id = demo-client
client_secret = ***
subject_token = <original access token>
subject_token_type = urn:ietf:params:oauth:token-type:access_token
requested_token_type = urn:ietf:params:oauth:token-type:access_token
scope = openid email profile (no 'roles'!)
Why move roles to optional scope?
In this demo, roles is an optional client scope in demo-client. When it is default, Keycloak always adds it regardless of the requested scope. Making it optional means the token exchange can produce a token without role claims.

{# Verify with resource server #} {% if exchange_result.success %}
Verify the rescoped token

The rescoped token still has a valid signature and sub — but because it has no realm_access.roles, the resource server will:

  • Accept it on GET /api/products (any valid JWT)
  • Reject it with 403 on GET /api/users/me (requires user-role)
  • Reject it with 403 on GET /api/admin/dashboard (requires admin-role)

To test this, copy the rescoped access_token above and use it in a tool like Insomnia or curl against http://localhost:8001.

Key takeaways
  • Downscoping lets you enforce least privilege — hand a sub-component only the permissions it actually needs.
  • The scope claim in the new token reflects the narrower set; realm_access.roles is absent.
  • The token is still cryptographically valid — the resource server trusts it, but role checks will return 403.
  • This only works when roles is an optional scope in the client (not default); see realm-export.json.
  • Requires KC_FEATURES=preview and Keycloak token-exchange permissions configured in the Admin Console.
