SPIFFE Workload Identity → OAuth2

A container proves its identity to SPIRE without any stored secret. The resulting JWT-SVID confirms runtime workload attestation. Keycloak 26.4+ then authenticates the service via RFC 7523 private_key_jwt — an in-memory EC key replaces the client_secret entirely.

How SPIFFE + OAuth2 Works
  1. SPIRE attests the workload — the SPIRE agent identifies the container using OS-level selectors (unix UID) and checks it matches a registered entry on the SPIRE server.
  2. JWT-SVID issued — SPIRE issues a short-lived (exp - iat ≈ 5 min) signed JWT whose sub is a SPIFFE URI (spiffe://demo.local/spiffe-service). No password or API key was ever stored.
  3. RFC 7523 private_key_jwt authentication — the service authenticates to Keycloak using a signed JWT assertion (client_assertion). Keycloak fetches the public key from GET /jwks on this service and verifies the ES256 signature. No client_secret is stored anywhere. The EC key pair is generated in-memory at container startup and never persisted.
  4. Protected API called — the resource server validates the OAuth2 token, confirms the bearer has user-role, and returns the product list.
SPIRE Workload API
→ JWT-SVID (spiffe://demo.local/spiffe-service)
Keycloak — RFC 7523 private_key_jwt
→ grant_type=client_credentials
→ client_assertion=<ES256 JWT>
← Keycloak fetches /jwks, verifies sig
→ access_token (no secret used)
Resource Server
→ Authorization: Bearer <access_token>
→ 200 OK (products)
{# Why SPIFFE? #}
Why SPIFFE Instead of Secrets?
Client Credentials SPIFFE / SPIRE
Secret stored in env var No stored secret
Long-lived credential Short-lived SVID (~5 min)
Secret rotation is manual Automatic renewal
Identity based on "what you know" Identity based on "what you are"
Secret can be leaked / copied SVID bound to attested workload

Architecture: before and after KC 26.4
Before KC 26.4 — bridge pattern (legacy)
1. SPIRE issues JWT-SVID
sub: spiffe://demo.local/spiffe-service
2. Bridge: validate SVID locally
SPIFFE ID → (client_id, client_secret)
3. POST /token grant_type=client_credentials
client_id + client_secret
← access_token (OAuth2)
(Secret stored in env var / config)
This demo — KC 26.4+ (RFC 7523 private_key_jwt)
1. SPIRE issues JWT-SVID (workload proof)
sub: spiffe://demo.local/spiffe-service
2. POST /token
grant_type=client_credentials
client_assertion_type=jwt-bearer
client_assertion=<ES256 JWT>
← KC fetches /jwks, verifies sig
← access_token (OAuth2)
(No secret anywhere — ephemeral EC key)
