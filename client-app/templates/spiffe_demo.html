SPIFFE Workload Identity → OAuth2

A container proves its identity to SPIRE without any stored secret. The resulting JWT-SVID is mapped to a Keycloak service account via the SPIFFE→OAuth2 bridge pattern, producing a standard OAuth2 access token that is then used to call the protected resource server.

{# ── LEFT: How it works ───────────────────────────────────────────────────── #}
How SPIFFE + OAuth2 Works
  1. SPIRE attests the workload — the SPIRE agent identifies the container using OS-level selectors (unix UID) and checks it matches a registered entry on the SPIRE server.
  2. JWT-SVID issued — SPIRE issues a short-lived (exp - iat ≈ 5 min) signed JWT whose sub is a SPIFFE URI (spiffe://demo.local/spiffe-service). No password or API key was ever stored.
  3. SPIFFE→OAuth2 bridge — the validated SPIFFE ID is mapped to a Keycloak service account. Keycloak issues a standard OAuth2 access token via client_credentials.
    (With Keycloak 26.4+ this step is eliminated — the JWT-SVID is presented directly as a client_assertion per RFC 7523.)
  4. Protected API called — the resource server validates the OAuth2 token, confirms the bearer has user-role, and returns the product list.
SPIRE Workload API
→ JWT-SVID (spiffe://demo.local/spiffe-service)
SPIFFE→OAuth2 Bridge
→ grant_type=client_credentials
→ access_token (OAuth2)
Resource Server
→ Authorization: Bearer <access_token>
→ 200 OK (products)
{# Why SPIFFE? #}
Why SPIFFE Instead of Secrets?
Client Credentials SPIFFE / SPIRE
Secret stored in env var No stored secret
Long-lived credential Short-lived SVID (~5 min)
Secret rotation is manual Automatic renewal
Identity based on "what you know" Identity based on "what you are"
Secret can be leaked / copied SVID bound to attested workload

Architecture note: Keycloak 26 vs 26.4+
This demo — Keycloak 26 (bridge pattern)
1. SPIRE issues JWT-SVID
sub: spiffe://demo.local/spiffe-service
2. Bridge: validate SVID locally
SPIFFE ID → (client_id, client_secret)
3. POST /token grant_type=client_credentials
← access_token (OAuth2)
Future — Keycloak 26.4+ (RFC 7523 direct)
1. SPIRE issues JWT-SVID
sub: spiffe://demo.local/spiffe-service
2. POST /token
grant_type=client_credentials
client_assertion_type=jwt-bearer
client_assertion=<JWT-SVID>
← access_token (OAuth2)
(No bridge, no stored secret)
