DPoP — Demonstrating Proof of Possession (RFC 9449)

A sender-constrained token that is cryptographically bound to a client-generated EC key pair. Even if the token is intercepted, it is useless without the matching private key.

{# ── LEFT — Concepts ──────────────────────────────────────────────────────── #}
How DPoP Works
  1. Client generates an ephemeral EC P-256 key pair.
  2. Client sends a DPoP proof — a short-lived signed JWT — along with every token request. The proof contains the public key, the HTTP method, the URI, a timestamp, and a unique jti.
  3. Keycloak validates the proof and embeds the public key's SHA-256 thumbprint (cnf.jkt) into the access token.
  4. For every API call, the client generates a new DPoP proof bound to that specific method + URL, plus the ath claim (SHA-256 of the access token).
  5. The resource server verifies both: the access token signature and the DPoP proof signature. The proof's public key thumbprint must match cnf.jkt in the token.
POST /token + DPoP: <proof₁>
← access_token (cnf.jkt = SHA256(pub_key))
GET /api/dpop-protected
Authorization: DPoP <access_token>
DPoP: <proof₂ (htm+htu+ath)>
← 200 OK (both token and proof verified)
Bearer vs DPoP
PropertyBearer (RFC 6750)DPoP (RFC 9449)
Token type Possession only Sender-constrained
Stolen token usable? Yes No
Auth header Bearer <token> DPoP <token>
Extra header None DPoP: <proof>
Token claim None cnf.jkt
Proof per request No Yes — bound to method + URL
Replay attack Possible Blocked by jti + iat
The Attack DPoP Prevents

With Bearer tokens:

If an attacker intercepts Authorization: Bearer eyJ… (e.g. via a compromised proxy or log file), they can replay it from any machine until it expires.

With DPoP:

The attacker also needs the private key. Without it, they cannot produce a valid DPoP proof. The intercepted token alone is worthless.

{# ── Key takeaways ─────────────────────────────────────────────────────────── #}
Key takeaways
  • A DPoP proof is a signed JWT generated per request — it is not reusable and carries no sensitive data.
  • The access token's cnf.jkt claim locks the token to one specific key pair — not one specific machine.
  • The ath claim in the API call proof prevents using the proof with a different token.
  • Each proof has a unique jti; resource servers can keep a short-lived set of seen JTIs to block replays within the freshness window.
  • DPoP is required by FAPI 2.0 (Financial-grade API) and is recommended by the OAuth 2.0 Security Best Current Practice (RFC 9700).
  • DPoP is GA in Keycloak 26.4+ — no feature flags required. The dpop.bound.access.tokens: true client attribute enforces DPoP binding for every token issued to that client.
