On-Behalf-Of (OBO) — RFC 8693 Token Exchange

A middle-tier service exchanges the user's access token for a new one that still represents the same end-user, but is now scoped to (and signed for) the middle-tier client. This lets downstream APIs know who the user is without the middle tier forwarding the original credential.

{# ── LEFT — How it works + exchange result ────────────────────────────────── #}
How On-Behalf-Of Works
  1. User authenticates → gets an access token from Keycloak.
  2. User calls the middle-tier API with that token.
  3. Middle tier calls Keycloak's token endpoint with grant_type=token-exchange, passing the user token as subject_token and authenticating itself with its own client_id + client_secret.
  4. Keycloak issues a new token:
    • sub still points to the original user
    • azp is now middle-tier-client
    • act (actor) claim records the delegation chain
  5. Middle tier forwards the new token to the downstream resource server.
POST /realms/demo/protocol/openid-connect/token
grant_type = urn:ietf:params:oauth:grant-type:token-exchange
client_id = middle-tier-client
client_secret = ***
subject_token = <user's access token>
subject_token_type = urn:ietf:params:oauth:token-type:access_token
requested_token_type = urn:ietf:params:oauth:token-type:access_token

{# ── Key takeaways ─────────────────────────────────────────────────────────── #}
Key takeaways
  • The sub claim (user identity) is preserved in the exchanged token.
  • The azp (authorized party) changes to middle-tier-client, recording which service made the exchange.
  • An act (actor) claim may appear, building a delegation chain auditable by downstream services.
  • Standard Token Exchange is GA in Keycloak 26.2+ — no feature flags required. The standard.token.exchange.enabled attribute on middle-tier-client is all that is needed.
