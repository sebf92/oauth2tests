Token Introspection (RFC 7662)

Resource servers can ask the Authorization Server in real time whether a token is currently active. Unlike local JWT validation, introspection detects revoked tokens even before they expire — at the cost of one extra network call per request.

RFC 7662 Response Fields

active: false means the token is currently invalid — either expired or revoked. The AS does not distinguish between the two in the response.

active true if usable right now; false otherwise
sub Subject — the user or service the token was issued to
username Human-readable username (Keycloak extension)
scope Space-delimited list of granted scopes
client_id The OAuth2 client that requested the token
token_type Bearer for standard access tokens
exp Expiry Unix timestamp — when the token would expire
iat Issued-at Unix timestamp
When to Use Introspection
  • Long-lived tokens — when access tokens have multi-hour lifetimes, revocation without introspection means a compromised token stays valid until expiry.
  • Shared resource servers — multiple APIs trusting one AS can each introspect rather than each managing key rotation.
  • Audit logging — the AS can record every introspection call, giving a complete picture of token usage across services.
  • Opaque tokens — reference tokens (non-JWT) carry no embedded claims; introspection is the only way to validate them.
  • Logout / session termination — after a user logs out, subsequent introspection calls for their tokens will return active: false immediately.

{# ── Why This Matters tab ─────────────────────────────────────────────── #}
Attack scenario — stolen access token after logout
  1. User logs in and obtains an access token with a 2-hour expiry.
  2. An attacker exfiltrates the token (compromised proxy, log file, XSS).
  3. The legitimate user notices and logs out — their session and refresh token are revoked in Keycloak.
  4. The attacker sends Authorization: Bearer <stolen_token> to the API.
  5. Without introspection: the API verifies the JWT signature and exp, sees it is not expired, and grants access for up to 2 hours post-logout.
    With introspection: the API asks the AS — which responds active: false — and rejects the request immediately.

Choosing the right strategy

StrategyTrade-offBest for
Short access token lifetime (1–5 min) More token refreshes High-security APIs
Introspection on every request Extra AS round-trip Long-lived or opaque tokens
Cached introspection (TTL = token exp) Slightly delayed revocation detection High-traffic resource servers
Local decode only No revocation detection Low-risk, offline APIs
RFC 9700 (OAuth 2.0 Security BCP) recommends keeping access token lifetimes short (minutes, not hours) as the primary defense, with introspection or token binding as additional layers for sensitive resources.

{# ── Key takeaways ─────────────────────────────────────────────────────────── #}
Key takeaways
  • active: false is intentionally ambiguous — the AS does not reveal whether a token expired or was revoked, preventing information leakage to callers.
  • Introspection is authenticated — the calling resource server must present its own client_id and client_secret (or a client assertion) to the AS.
  • A structurally valid, unexpired JWT can still be active: false — local decode alone is not a complete security check when revocation matters.
  • Keycloak's introspection endpoint returns full JWT claims for active tokens, so resource servers do not need to decode the token separately.
  • For high-traffic services, cache introspection responses with a TTL of 30–60 seconds to reduce AS load while keeping the revocation window short.
