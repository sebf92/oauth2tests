OpenID Connect — Identity Layer

OpenID Connect (OIDC) adds a thin identity layer on top of OAuth2. Where OAuth2 only answers "can this client access that resource?", OIDC also answers "who is the user?" — via the id_token, the UserInfo endpoint, and a standardised Discovery document.

OIDC Claims Glossary
sub Subject — stable, unique user identifier (UUID)
iss Issuer — the URL of the Keycloak realm that signed the token
aud Audience — who the token is intended for
azp Authorised party — the client that requested the token
iat Issued at — Unix timestamp when the token was created
exp Expiry — Unix timestamp after which the token is invalid
nonce One-time value set by the client to prevent replay attacks
email User's verified email address
preferred_username Human-readable username (e.g. alice)
name Display name (given_name + family_name)
auth_time Time the user actually authenticated with Keycloak
session_state Keycloak SSO session ID (absent in Client Credentials)

{# ── UserInfo tab ──────────────────────────────────────────────────────── #}

The UserInfo endpoint is a protected resource server that returns claims about the authenticated user. Unlike the id_token (which is embedded in the token response), UserInfo is fetched via a live HTTP request using the access_token.

{# Request box #}
GET {{ userinfo_url }}
Authorization: Bearer <access_token>
{# Response #}
{{ userinfo_status }} {{ 'Response' if userinfo_ok else 'Error' }} 
{{ userinfo | tojson(indent=2) }}
{% if userinfo_ok %}
Why use UserInfo instead of the token? Token claims are baked in at issuance and may be stale. UserInfo is a live call that always reflects the current profile. Useful when user attributes change frequently or when you need claims beyond what the token scope includes.
{% endif %}

The OIDC Discovery document (/.well-known/openid-configuration) is a JSON object that describes the Identity Provider's capabilities and all its endpoint URLs. Clients use it to auto-configure — no hard-coded URLs needed.

{# ── Key takeaways ─────────────────────────────────────────────────────────── #}
Key takeaways
  • Add the openid scope to any OAuth2 request to opt into OIDC — you'll get an id_token back.
  • The id_token is for your client application only — never forward it to an API.
  • The UserInfo endpoint always returns live claims; the id_token is a snapshot at login time.
  • The Discovery document lets clients auto-configure without hard-coded URLs — the basis of portable OIDC libraries.
  • Client Credentials does not produce an id_token — there is no user, so there is no identity to assert.
